# EXAM SAFE PASS — 공모전 시제품

가상 응시자와 명부, 감독관 수동 대조를 이용하는 시연용 웹앱입니다. 서버와 데이터베이스는 Python 표준 라이브러리 HTTP 서버와 SQLite를 사용하고, QR 이미지 생성에 `qrcode` 패키지를 사용합니다. 공식 모바일신분증 provider/승인 정보는 제공되지 않았으므로 실제 연동은 미완료이며 운영 인증은 차단됩니다. 키오스크 셀프 DEMO에는 브라우저에서 실제 실행되는 Human Antispoof 모델을 연결한 실험용 PoC가 있습니다. 이 PoC는 검증된 대리응시 방지 수단이 아닙니다.

> **공모전 시제품 · 실제 신원인증 아님**. 공식 기관의 승인이나 실제 신원확인 절차가 없으며, 화면 결과는 실제 입실 자격을 부여하지 않습니다. 공식 모바일신분증 인증·정부 시스템 연동·검증된 얼굴 인증·대리응시 판별은 구현되어 있지 않습니다. 얼굴 유사도와 안티스푸핑 점수는 브라우저 안에서 실행되는 연구용 참고 출력이며, 운영 인증에 사용되지 않습니다. 모든 인물과 정보는 가상 데이터입니다. 실물 신분증 사진·번호·생년월일 등 민감한 개인정보는 입력·저장하지 않습니다. QR에는 개인정보가 아닌 서버 발급 임의 토큰만 포함됩니다.

### 운영/DEMO 경계 (fail closed)

모의 모바일신분증 결과는 `demo_mobile_id_auth`에만 저장하며, DEMO QR은 `demo_tokens`, 모의 입실은 `demo_admissions`에만 기록합니다. `/api/token`, `/api/token/inspect`, `/api/approve`는 DEMO 증명·토큰을 거부합니다. 실물 신분증 모의 판정, 책임자 예외, 감독관 키오스크 시연 또한 운영 `admissions`를 생성하지 않습니다. 현재 `OFFICIAL_MOBILE_ID_PROVIDER`는 미설정이고 `INSTITUTION_ADMISSION_POLICY_APPROVED`는 비활성화되어 있으므로 공식 인증·운영 QR·운영 입실 승인은 서버에서 거부됩니다. 공식 provider 어댑터 계약은 서명 검증 근거, 검증 출처와 키 ID, 요청/거래번호, 발급·만료시각, 명부 응시자 일치 여부뿐 아니라 서명된 liveness 검증 출처·모델 버전·점수/임계값·응시자/요청 바인딩·유효기간도 요구합니다. 서버는 identity/liveness 거래번호 재사용을 각각 거부합니다. 다만 실제 공식 서명 검증기·신뢰 검증키와 신뢰 가능한 서버측 실재성 검증기가 구성되지 않아 이 경로는 현재 사용할 수 없습니다. 브라우저 DEMO의 얼굴 프레임이나 점수는 운영 API로 보내지 않습니다. 운영 승인은 기관 정책, 공식 신원검증, 신뢰 가능한 운영용 실재성 증명이 모두 갖춰질 때까지 차단합니다.

## 공식 모바일신분증 연동 준비 상태

공식 문서 확인 기준: [모바일신분증 개발지원센터](https://dev.mobileid.go.kr/mip/dfs/dfsmain.do), [연계서비스 이용 가이드](https://dev.mobileid.go.kr/mip/dfs/useguide/mdGuide.do?guide=cntcuseguide), [개발지원센터 안내/문의](https://dev.mobileid.go.kr/mip/dfs/apiuse/apiuseinfo.do).

- 개발지원센터는 연계 서비스 기관을 대상으로 이용 절차, 개발 규격/가이드, 신청 및 라이브러리를 제공합니다. 공개 사이트에서 이 저장소가 직접 사용할 공개 API·SDK·테스트 인증정보는 확인되지 않았습니다.
- 공식 가이드에 따라 기관 회원가입 및 승인, 연계서비스 신청서와 필수 공문 제출, 개발 DID 등록 신청과 승인, 개발계 연계 테스트가 선행되어야 합니다. 가이드에는 개발계 연계 증적 제출 후 운영 DID를 신청하는 단계가 안내되어 있습니다.
- 테스트베드 앱/테스트 신분증, 공식 SDK·라이브러리, 기관별 테스트 인증정보, 검증키/인증서, 실제 메시지 규격 및 응답 서명 검증 방식은 승인된 개발지원센터 계정으로 제공/확인해야 합니다. 이 저장소에는 이 자료나 비밀정보가 없으며 임의 키·응답을 만들어 운영 증명으로 취급하지 않습니다. 테스트베드앱 연계 흐름 검증자료도 없습니다.
- 적용 전에 기관 승인과 이용 목적/개인정보 처리 적합성을 확인하고, 승인된 규격에 맞는 서버측 verifier를 구현해야 합니다. verifier는 공식 출처·키 ID로 서명과 발급자/대상, 응시자 식별자, nonce/request ID, 고유 거래번호, 발급/만료시각을 검증해야 하며 거래 재사용을 차단해야 합니다. 수집 속성은 필요한 최소 정보로 제한해야 합니다.
- 개발지원센터 문의처(공식 페이지 표기): 042-870-1498~9, `mid_apply@komsco.com`.
- `OfficialMobileIdProvider`는 공식 신원증명과 독립된 검증 liveness 증명을 전달하는 어댑터 계약일 뿐, 제공된 공식 SDK나 실제 연동 구현이 아닙니다. 응답에 두 증거 중 하나라도 없거나 요청/응시자·서명·거래번호·점수·유효기간 검증이 실패하면 서버는 승인하지 않습니다. 현재 `/api/mobile-id/official-authenticate`는 provider가 없으면 503으로 거부합니다. 이를 운영 가능으로 바꾸지 않았습니다.

## 실행

Python 3.10 이상에서 저장소 루트에서 의존성을 설치하고 실행합니다.

```sh
python3 -m pip install -r requirements.txt
python3 server.py
```

브라우저에서 <http://127.0.0.1:8000/>을 엽니다. 키는 서버 로그에 출력되지 않으며 아래 '로그인 계정과 비밀정보 설정' 절차로 직접 설정해야 서버가 시작됩니다. 키오스크 화면은 <http://127.0.0.1:8000/kiosk>에서 실행합니다. 브라우저의 로그인 버튼 또는 입력 필드에 넣어 세션을 만들 수 있습니다. 환경변수 `EXAM_SAFE_CANDIDATE_KEY`, `EXAM_SAFE_PROCTOR_KEY`, `EXAM_SAFE_ADMIN_KEY`를 설정하면 키를 직접 지정할 수 있습니다. 키와 계정 정보는 공개 저장소에 저장하거나 실제 비밀키를 사용하지 마세요. QR 디코더는 `/vendor/qr-decoder.min.js`에서 로컬로 제공되므로 실행 시 외부 CDN이나 인터넷 연결이 필요하지 않습니다.

활성 테스트는 `tests/` 디렉터리에만 두고, 역사적 백업 스냅샷은 `test_backups/`에 보관합니다. 기본 실행은 다음과 같이 합니다.

```sh
pytest -q
```

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
```

## 로그인 계정과 비밀정보 설정 (필수)

서버에는 기본 계정·비밀번호·API 키가 없습니다. 관리자 비밀정보(`EXAM_SAFE_ADMIN_PASSWORD_HASH`, `EXAM_SAFE_ADMIN_KEY`)가 없거나 과거 기본값·약한 값이면 서버가 시작되지 않습니다(종료 코드 2).

1. 본인 터미널에서 `python3 tools/generate_secrets.py` (역할 지정: `--role proctor`, 직접 입력: `--prompt`)를 실행합니다. 출력은 한 번만 표시되므로 저장·공유하지 마세요.
2. 출력된 `EXAM_SAFE_<ROLE>_PASSWORD_HASH`, `EXAM_SAFE_<ROLE>_KEY` 값을 GitHub > Settings > Codespaces > Secrets(저장소 접근 허용)에 등록하고 Codespace를 재시작합니다. 로컬에서는 추적되지 않는 `.env`에 둘 수 있습니다(`.env`는 `.gitignore` 대상).
3. 변수 이름 목록은 `.env.example`을 참고하세요(값 없음). 감독관·응시자·현장 책임자 역할은 값을 설정한 경우에만 활성화됩니다. 계정 ID는 `EXAM_SAFE_<ROLE>_USERNAME`(기본 `<role>-demo`)입니다.
4. 비밀번호는 scrypt 해시로만 저장·비교하며 평문은 서버 설정에 두지 않습니다. 이전 버전의 기본 계정/키는 Git 기록에 남아 있으므로 **사용하지 말고 새 값으로 교체**하세요.

브라우저에서 각 역할 화면에 설정한 키/계정을 입력하거나 다음처럼 로그인할 수 있습니다(값은 본인 Secrets 값).

```sh
curl -X POST http://127.0.0.1:8000/api/login \
  -H 'Content-Type: application/json' \
  -d '{"role":"proctor","demo_key":"<PROCTOR_KEY>","username":"<PROCTOR_USERNAME>","password":"<PASSWORD>"}'
```

로그인 실패는 클라이언트 주소·역할별로 속도 제한(기본 5회/300초)됩니다. 상태 변경 요청은 `Origin` 허용 목록(`EXAM_SAFE_ALLOWED_ORIGINS`, Codespaces 포워딩 주소는 환경에서 자동 유도)과 쿠키 세션의 CSRF 토큰(`X-CSRF-Token`)을 모두 검사합니다. 세션은 SQLite(`session_store`)에 저장되어 재시작 후에도 만료 시각이 유지됩니다(세션 ID는 해시만 저장).

로그인하면 서버가 `demo_session_id` 쿠키를 발급하고 다음 API 호출에서 역할 기반 권한을 확인합니다. 현장 책임자 키는 `EXAM_SAFE_SUPERVISOR_KEY`로 지정할 수 있습니다. 기존 호환성을 위해 `X-Demo-Role`과 `X-Demo-Key` 헤더도 계속 지원합니다.

응시자 화면에서 모의 인증을 누르면 서버가 실제 PNG QR 이미지와 30초 카운트다운을 표시합니다. QR 내용은 `secrets.token_urlsafe(32)`로 만든 일회용 토큰뿐입니다. 감독관은 `getUserMedia()` 카메라 스캔, QR 이미지 파일 업로드, 또는 수동 토큰 입력을 사용할 수 있습니다. 지원 브라우저에서는 `BarcodeDetector`를 우선 사용하고, 미지원이거나 QR 입력 소스를 지원하지 않으면 프로젝트에 포함된 ZXing for JS 디코더로 자동 전환합니다. QR 이미지 파일은 브라우저 메모리에서 판독하고 파일 자체는 서버로 전송하지 않습니다. 판독한 토큰은 기존 토큰 확인 API로 전송되어 서버에서 시험·응시자·만료·재사용 상태를 검사합니다. 카메라 사용에는 HTTPS 또는 localhost와 사이트 카메라 권한이 필요하지만 이미지 업로드 및 수동 입력은 카메라 권한 없이 사용할 수 있습니다. 업로드 이미지는 15MB 이하로 제한합니다.

서로 다른 기기에서 QR을 보여주고 스캔하려면 신뢰할 수 있는 로컬 네트워크에서 서버를 `EXAM_SAFE_HOST=0.0.0.0 python3 server.py`로 실행합니다. 응시자 기기는 서버 PC의 LAN 주소(`http://<서버-LAN-IP>:8000`)로 접속해 QR을 띄우고, 카메라를 쓸 감독관 브라우저는 서버 PC에서 `http://localhost:8000`으로 접속하면 localhost 카메라 권한 조건을 만족합니다. 이 시연 서버는 HTTP이므로 신뢰하지 않는 네트워크에 노출하지 마세요. 다른 기기에서 감독관 카메라를 쓸 경우 HTTPS가 필요합니다.

## 공용 인증 키오스크 시연

1. PC에서 서버를 실행하고 <http://127.0.0.1:8000/kiosk>를 연 뒤 브라우저 전체화면(F11)을 사용합니다. 설치형 키오스크 모드에서는 브라우저를 `--kiosk` 옵션으로 실행할 수도 있습니다. 같은 서버의 감독관 화면은 일반 창에서 `/`를 열고 **감독관** 탭에서 로그인합니다.
2. 첫 화면에는 **셀프 인증 시작**과 **감독관 인증**만 표시됩니다. 관리자 도움 요청과 세션 종료는 화면 아래에 있습니다.
3. 휴대전화 없음 경로에서는 가상 수험번호를 조회합니다. 번호는 명부 조회용일 뿐, 단독으로 인증을 완료하지 않습니다. 감독관은 키오스크 요청 목록을 새로고침해 가상 등록 사진을 보고, 허용된 모의 문서 종류와 실물 신분증·현장 얼굴을 직접 비교해 판정합니다. 시제품의 내부 허용 목록(주민등록증·운전면허증·여권)은 공식 기관의 실제 허용 정책을 의미하지 않습니다.
4. 감독관 판정이 승인인 경우에도 키오스크 시연은 DEMO 전용 임의 일회용 QR만 발급합니다. 키오스크 세션은 서버에서 관리하고, DEMO 토큰은 DB에 해시로 기록되며 30초 후 만료됩니다. DEMO 재발급 시 기존 토큰을 무효화합니다. 모의 입실은 `demo_admissions`에만 기록되고 실제 입실 승인 API에서는 거부됩니다.
5. 신분증 불일치와 대리응시 의심은 거부 기록으로 남고 QR이 발급되지 않습니다. 신분증 없음, 모의 허용 목록 외 문서, 신원확인 불가는 **현장 책임자 확인 대기**로 기록되며 자동 승인되지 않습니다. 확인 결과 reason 값이 `normal`이 아니거나 세션에 유효한 감독관 승인 시각이 없는 경우 서버는 QR 발급을 거부합니다.
6. 세션 종료 버튼, 3분 무입력 자동 초기화, 처음 화면 이동 및 페이지 종료 시 키오스크 세션을 서버에서 폐기합니다. 키오스크 브라우저는 현재 세션 식별자만 `sessionStorage`에 두며 수험번호, 이름, 사진, QR을 브라우저 저장소에 기록하지 않습니다. 미사용 운영 QR 및 화면용 DEMO QR은 세션 종료/폐기 시 무효화됩니다. 단, 출력용 DEMO QR은 인쇄 후 이동 시간을 고려해 서버 만료시각까지 유효하며, 세션이 종료된 후에도 모의 입실 검증 API에서 1회 처리할 수 있습니다. 이 토큰은 실제 입실에 사용할 수 없습니다. 종료되지 않은 서버 세션도 마지막 접근 후 3분 내 만료됩니다. 서버 메모리의 응시자 정보는 시연 프로세스 내에서만 유지됩니다.
7. 관리자 도움 요청은 이벤트 로그에 남기며, 실제 호출 장치나 공식 관리자 시스템을 연동하지 않습니다.

### 셀프 DEMO와 감독관 확인 모드

- 셀프 흐름은 수험번호 조회 → 브라우저 내 얼굴 비교와 Antispoof PoC 실행 → 점수 표시 → 분리된 DEMO 모의 테스트 선택 → QR 화면/출력 선택 순서입니다. 얼굴 영상·임베딩·점수는 서버로 전송하지 않습니다. 브라우저 결과는 서버 검증된 인증 근거가 아니며, 운영 QR을 발급하지 않습니다. 얼굴 미검출·복수 얼굴·모델 미로딩/오류/점수 누락·위조 의심은 실패 처리되고 DEMO 다음 단계도 표시하지 않습니다. DEMO 완료 API는 얼굴 점수/일치/성공 주장을 계속 거부합니다.
- 얼굴 비교와 PoC 점수 통과만으로 인증을 완료하지 않습니다. 별도 `DEMO 모의 성공으로 진행` 버튼은 시연용 QR을 위한 모의 성공을 명시적으로 서버에 요청합니다. 이 요청은 운영 인증이 아니고 서버에서 `demo_authenticated` 상태로만 기록됩니다. 운영 provider/기관 정책/운영용 검증 실재성 검사가 제공되지 않아 운영 입실 QR은 발급되지 않습니다. QR 입실권 출력에는 `공모전 시제품 · 실제 입실 불가` 표시가 포함됩니다.
- 응시자 화면에는 네 가지 결과 시나리오 선택기 및 시연용 QR 미리보기가 없습니다. DEMO 성공은 얼굴 비교와 별도의 명시적 버튼으로 선택하며, 성공/실패/불확실/불일치 시나리오 테스트는 관리자 로그인 후 관리자 화면에서만 가능합니다. 관리자 테스트 API는 서버에서 권한을 확인하고 이벤트로 감사 기록을 남깁니다.
- 화면 QR은 30초, 출력용 DEMO QR은 기본 900초(15분) 유효한 `DEMO-ONLY:SELF:` QR이며 `EXAM_SAFE_KIOSK_PRINT_QR_TTL_SECONDS` 환경변수로 설정할 수 있습니다(최소 30초). 토큰은 예측 불가능한 값으로 생성되고 DB에는 해시만 기록하며, 응시자 개인정보는 QR에 넣지 않습니다. 인쇄 메타데이터는 응시권에 표시됩니다. 새 출력 QR을 발급하면 기존 토큰을 무효화하고, 만료·사용·중복 입실 여부는 서버에서 검사합니다. **모의 입실 처리**는 별도 DEMO 기록만 남기며 `real_admission: false`를 반환합니다. 일반 토큰 검사·감독관 승인 API는 이 QR을 거부합니다.
- 화면의 **화면으로 QR 보기**와 **QR 입실권 출력**은 별도 선택입니다. 인쇄 화면은 A4/영수증형 80mm 레이아웃과 브라우저의 인쇄/PDF 저장을 지원합니다. 재출력은 같은 유효 QR을 인쇄하며 새 토큰 발급은 하지 않습니다. 만료 후 재발급 시 서버가 이전 토큰을 무효화합니다. 인쇄 취소는 서버 토큰 상태를 바꾸지 않습니다. 종이 QR은 복사/전달될 수 있으므로 실제 운영에서는 입실구의 등록 사진·현장 얼굴 대조 및 1회 사용 차단이 필요합니다. 현재 DEMO QR은 실제 입실에 사용할 수 없습니다.
- **감독관 인증**은 기존 신원확인 시연 절차와 서버 역할 검증을 유지하지만, 발급되는 QR은 `DEMO-ONLY:KIOSK-PROCTOR:` 토큰입니다. QR 검사와 모의 입실은 전용 DEMO API·`demo_tokens`·`demo_admissions`로만 처리하며 운영 입실 API 및 `admissions`와 분리됩니다. 물리 신분증·책임자 예외 시연도 운영 입실 기록을 생성하지 않습니다. 감사 이벤트는 DEMO 경로임을 구분해 남깁니다.
- 공식 인증 provider를 향한 확장 경계는 [`self_identity_provider.py`](./self_identity_provider.py)의 `SelfIdentityProvider`/`SelfIdentityResult`입니다. 실제 provider가 없으면 미설정 결과는 `uncertain`이고 자동 승인 게이트를 통과하지 못합니다. 운영 자동 입실은 향후 공식 provider의 공식 결과, 응시자 일치, 검증된 실재성 검사와 기관 정책 승인이 모두 참인 경우에만 설계상 허용됩니다. 현재는 운영 인증 경로가 없으며 자동 실입실을 차단합니다.
- 세션 종료·자동 초기화·페이지 종료 시 키오스크가 카메라 트랙을 중지하고 QR 표시와 현재 사용자 정보를 지웁니다. 모든 경로에서 주민등록번호 전체를 요구하지 않습니다.

PC에서 셀프 DEMO는 `/kiosk`에서 **셀프 인증 시작** → 가상 수험번호 `2026-0012` → 카메라로 촬영 후 얼굴 비교 → 별도 DEMO 모의 성공 선택 → **화면으로 QR 보기** 또는 **QR 입실권 출력** 순으로 진행합니다. 인쇄 버튼은 PDF 저장을 포함하며 프린터 연결 검증은 별도로 필요합니다. 실제 카메라를 쓸 때는 `localhost` 또는 HTTPS와 브라우저 카메라 권한이 필요합니다. 결과별 실패·불확실·불일치 시나리오는 `/`의 **관리자** 화면에 로그인한 뒤 관리자 전용 키오스크 DEMO 테스트에서 실행합니다.

### 셀프 DEMO 얼굴 비교 및 안티스푸핑 PoC

- **실제 공격 탐지 실패 기록 (2026-10-28):** 브라우저 실험에서 실제 본인 얼굴은 유사도 50%/Anti-Spoof 0.75, 휴대전화 화면의 본인 사진은 80%/0.84, 휴대전화 화면의 다른 사람 사진은 40%/0.69로 모두 `live_candidate`가 되었습니다. 이는 Human 3.3.6 단일 프레임 모델이 화면 재촬영 공격을 놓친 사례입니다. 모의 점수를 자동 테스트에 기록하지만 실제 탐지율이나 보안 성능을 주장하지 않습니다.
- 얼굴 유사도 40%·50%·80%는 FaceRes 임베딩 비교 함수가 반환한 0~1 범위의 참고용 연속 점수를 백분율로 표시한 값일 뿐입니다. 시험장 데이터로 보정·검증된 동일인 임계값이 없으므로 현재 UI는 `일치 가능성 높음`/`불일치`로 판정하지 않고 `참고용 유사도 수치 · 본인 여부 미확인`만 표시합니다. 얼굴 점수와 단일 프레임 `live_candidate`만으로 셀프 인증·QR 발급을 진행하지 않으며, 판정 불가·검증 실패·공격 의심은 감독관 확인으로 전환합니다.
- 추가 PAD 검토: 화면 재촬영에는 단일 프레임 분류기보다 여러 프레임의 시간적 일관성·깊이/반사·디스플레이 경계 신호를 결합하는 다중 프레임 분석이 더 적합할 수 있습니다. 다만 이 저장소에는 검증된 추가 모델이나 브라우저용 SDK가 없으므로 임계값 상향이나 임의 모델 추가로 우회하지 않았습니다. 후보를 도입하려면 출처·가중치/학습 데이터 권리·라이선스, WebGL/WASM 및 대상 브라우저 호환성, 재현 가능한 실제 화면 공격 데이터셋의 FAR/FRR·ROC·하위그룹 검증, 운영 장애 시 fail-closed 증적을 먼저 확보해야 합니다. 현재 Human 모델의 출처·MIT 고지·브라우저 실행 방식은 [`MODEL-SOURCES.txt`](./vendor/human/models/MODEL-SOURCES.txt)에 기록되어 있지만 원본 Kaggle 권리·보정·공격 유형별 성능은 확인되지 않았습니다. 검증된 SDK 계약과 서버측 검증 증명이 확보되기 전까지 `live_candidate`는 신원확인 성공으로 취급하지 않습니다.
- 후보 조사 결과 (2026-10-28):
  - [MiniVision Silent-Face-Anti-Spoofing / MiniFASNet](https://github.com/minivision-ai/Silent-Face-Anti-Spoofing): 화면·인쇄 사진을 목표로 하는 공개 RGB PAD 프로젝트이며 Apache-2.0 저장소와 APK/모델 파일, 프로젝트가 보고한 FPR/TPR 수치가 있습니다. 그러나 공식 배포물은 Python/Caffe와 Android 중심이고 브라우저용 WebAssembly/ONNX 패키지·대상 브라우저 검증·독립적인 화면 재촬영 데이터 검증은 확인하지 못했습니다. 원본 모델을 브라우저에 변환해 추가하는 것은 현재 요구사항의 “실제 사용 가능 확인” 기준을 충족하지 못하므로 통합하지 않았습니다.
  - [MediaPipe Face Landmarker Web](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker/web_js): Apache-2.0 계열의 브라우저 실행 가능한 랜드마크/표정 도구이지만 PAD 모델이 아닙니다. 눈 깜빡임·표정·랜드마크만으로 사진/영상 재생 공격을 판정할 수 없으므로 보조 관찰 도구 후보일 뿐 인증 게이트 후보가 아닙니다.
  - [DeepFace](https://github.com/serengil/deepface): 얼굴 인식/속성 분석 라이브러리로서 PAD SDK가 아니며 브라우저 모델 배포·화면 공격 성능 자료가 이 용도에 맞게 제공되지 않습니다. 얼굴 유사도 대체 모델로 추가하지 않았습니다.
  - 상용 PAD SDK는 공급업체의 브라우저/생체정보 처리 계약, 모델 파일 또는 호스팅 방식, 라이선스, APCER/BPCER·공격 자료와 브라우저별 검증 보고서를 받아야 비교할 수 있습니다. 공개적으로 재현 가능한 자료와 저장소 내 모델 파일이 없는 상태에서는 특정 SDK를 “검증 완료”로 표시하지 않았습니다.
- 실행 라이브러리는 `@vladmandic/human` 3.3.6 (package.json/package-lock.json 고정)이고 MIT License 전문은 [`vendor/human/LICENSE`](./vendor/human/LICENSE)에 있습니다. 기존 BlazeFace 검출과 HSE FaceRes 임베딩 비교 기능은 유지했습니다. 안티스푸핑은 Human 3.3.6의 `face.antispoof` 경로에 연결한 **Human Anti-Spoofing / Real-of-Fake** 단일 프레임 모델입니다. `antispoof.bin`/`.json`을 GitHub Human Models 저장소 revision `bc66dc53bac03c96d35a7e6daaf717e72f3985f5`에서 받아 로컬 제공하며, 모델 저장소 MIT 고지와 SHA-256은 [`vendor/human/models/MODEL-SOURCES.txt`](./vendor/human/models/MODEL-SOURCES.txt)에 기록했습니다. 별도 Python/JS 의존성은 추가하지 않았습니다. 모델 문서가 출처로 든 원본 Kaggle 모델의 별도 권리·학습자료 조건은 독립 확인되지 않았으므로, 배포/상업/운영 사용 전 권리 확인이 필요합니다.
- 얼굴 비교 점수는 Human descriptor similarity 함수이며 0.4, Antispoof 단일 출력은 0.5를 참고용 PoC 기준으로 표시합니다. 둘 다 시험장 데이터로 보정·검증하지 않은 임의 기준입니다. Human 모델 출처는 [모델 문서](https://github.com/vladmandic/human/wiki/Models) 및 [Human Models 저장소](https://github.com/vladmandic/human-models)에서 확인할 수 있습니다.
- Anti-Spoofing model의 단일 이미지 점수는 실제 입력 프레임의 실제 모델 출력입니다. 단순 눈 깜빡임 판정은 사용하지 않습니다. 그러나 이것은 사진/화면 재생 공격을 신뢰성 있게 차단한다고 입증된 결과가 아닙니다. FAR/FRR, APCER/BPCER, 데이터셋별 성능, 편향/접근성 분석 또는 제3자 검증 자료가 없고 화면 점수는 서버에 보내지 않습니다. 운영 입실은 이 점수를 신뢰하지 않으며 계속 차단됩니다.
- 수동 PoC 검증 시나리오: (1) 얼굴 없는 장면은 `face_missing`, (2) 두 명 이상은 `multiple_faces`, (3) 인쇄 사진을 카메라에 제시해 실제 점수/오판을 기록, (4) 다른 화면에서 정지 사진·정지 영상 및 움직이는 얼굴 영상을 재생해 각각 점수를 기록, (5) 실제 정상 얼굴에서 점수를 기록합니다. 현재 테스트는 상태 분류, 임계값, 누락/NaN/복수 얼굴의 fail-closed 동작을 자동 검증하지만, 실제 카메라 공격군이나 정상 사용자에 대한 성능 시험은 수행하지 않았습니다. 이 시나리오 수행 전에는 모델 성능이나 대리응시 방지를 주장하지 않습니다.
- 장애/모델 파일 누락 시 PoC는 성공이 아니라 `liveness_unavailable`로 나타나고 DEMO 진행 버튼도 숨깁니다. DEMO API는 독립된 명시적 모의 경로로만 동작하며 운영 `admissions`, 운영 토큰, 운영 인증상태와 결합되지 않습니다.

소스/번들 재생성은 Node.js 18 이상에서 다음과 같이 합니다. 애플리케이션 실행은 생성된 로컬 번들을 사용하므로 Node.js가 필요하지 않습니다.

```sh
npm ci
npm run build:face
```

### 일반 PC 브라우저에서 전체 흐름 확인

실제 키오스크 장비 없이 같은 PC에서 두 브라우저 창/탭으로 진행할 수 있습니다.

1. 저장소 루트에서 `python3 server.py`를 실행합니다. 브라우저 A에서 <http://127.0.0.1:8000/kiosk>를 열고 F11을 눌러 전체화면으로 전환합니다. Chrome/Edge 키오스크 실행 옵션을 사용하는 경우 예: `google-chrome --kiosk http://127.0.0.1:8000/kiosk` (설치된 브라우저 실행 파일 이름은 환경에 따라 다릅니다).
2. 브라우저 B에서 <http://127.0.0.1:8000/>을 열고 **감독관** 탭에서 감독관 키로 로그인합니다. `EXAM_SAFE_PROCTOR_KEY`로 설정한 값을 사용합니다.
3. 브라우저 A에서 **감독관 인증**을 누르고 가상 수험번호 `2026-0012`를 입력합니다. 이 조회만으로는 인증되지 않습니다. 브라우저 B의 감독관 탭에서 **키오스크 확인 요청 새로고침**을 눌러 요청을 확인합니다.
4. 응시자와 대면한 시연 상황에서 감독관은 실제 자동판독 없이 허용된 모의 문서 종류(예: 주민등록증)를 선택하고 **신분증·현장 얼굴 일치**를 판정해 제출합니다. 승인되지 않은 역할의 요청은 서버가 거부하고 토큰을 만들지 않습니다. 승인되면 브라우저 A에 개인정보 없는 일회용 QR이 표시됩니다. 발급 순간부터 서버 기준 30초이며 만료 시 화면에서 사라집니다.
5. 입실구 재확인은 브라우저 B의 기존 감독관 QR 스캐너 기능에서 수행합니다. 카메라가 없으면 QR이 표시된 브라우저 A 화면을 PNG 스크린샷으로 저장해 감독관 화면의 **QR 이미지 파일로 확인**에 올립니다. 스크린샷 저장이 어렵다면 키오스크 QR 화면을 OS 캡처 도구로 잘라 PNG로 저장하면 됩니다. 업로드 이미지는 로컬 브라우저에서 판독하고 토큰은 서버의 `/api/token/inspect`로 검증합니다. 카메라 대신 직접 API를 점검하려면 아래 자동 통합 시나리오가 PNG를 ZXing으로 판독한 토큰을 실제 검사·승인 API에 제출합니다.
6. QR 서버 검증이 끝나면 감독관은 명부 일치 확인과 현장 얼굴 대조 결과를 다시 선택하고 **입실 승인 요청**을 누릅니다. 스캔만으로는 입실되지 않습니다. 마지막으로 관리자 탭에서 서버 기록 새로고침을 눌러 승인 이벤트를 확인합니다.
7. 30초 만료, 재사용, 잘못된 시험 정보, 승인 전 발급 시도, 중복 입실 차단은 아래 자동 테스트가 임시 DB와 서버 API로 검증합니다. 실제 30초 대기 동작도 수동 확인하려면 승인 뒤 QR을 스캔하지 않고 31초 이상 기다립니다. 만료 QR은 서버에서 거부되며, 신원확인 승인 시각이 유효한 경우에만 감독관이 새 QR을 요청할 수 있습니다. 새 QR이 발급되면 이전 토큰은 사용 처리되어 재사용할 수 없습니다.

전체 서버 API 자동 흐름과 DB 상태는 다음으로 검증합니다.

```sh
npm ci
python3 -m unittest discover -s tests -v
python3 test_scenarios.py
```

`test_scenarios.py`는 테스트 전용 임시 SQLite DB와 임시 포트로 실제 `server.py`를 띄웁니다. 키오스크 조회, 감독관 권한 전/후 QR 발급, QR PNG를 로컬 `@zxing/library`로 디코딩, 잘못된 시험 차단, 최종 `/api/approve`, 토큰 소비·입실행·감사 이벤트 저장을 확인합니다. 만료는 테스트 시간을 단축하기 위해 테스트 DB의 토큰 만료시각을 과거로 설정한 다음 실제 inspect/refresh API가 만료 처리하는지 확인합니다. QR의 30초 수명 자체는 발급 API 응답과 DB 만료 시각도 검사합니다. 패키지 설치 없이 기존 `node_modules`가 준비된 개발 환경이면 `npm ci`는 생략할 수 있습니다.

**실기기/브라우저 결과:** 이번 검증 환경에는 Chromium/Chrome/Firefox 바이너리와 브라우저 자동화 도구가 없어 실제 브라우저 화면 상호작용, 전체화면 키오스크 모드, QR 이미지 업로드 버튼 클릭은 실행하지 못했습니다 (**미검증**). PC에서 위 순서로 직접 확인할 수 있습니다. 카메라 없는 자동 API 시나리오는 QR 이미지를 로컬 디코더로 읽어 서버의 실제 QR 검사·승인 경로를 확인하지만, 물리 카메라·프린터·키오스크 전용 하드웨어 동작은 검증하지 않습니다.

카메라 권한이 거부되거나 장치가 없는 경우 키오스크는 판정 불가를 표시하고 실제 인증으로 간주하지 않습니다. `python3 test_scenarios.py`는 QR 만료·재사용·재발급·중복 입실 차단, 관리자 권한 검증, 출력용 TTL, 실제 입실 기록과 분리된 모의 입실 및 감사 이벤트를 서버 API와 SQLite 상태로 검증합니다. 실제 프린터 출력은 테스트 환경에 프린터가 없어 검증하지 않았습니다.

시연용 QR 미리보기는 응시자 키오스크 화면에서 제거했습니다. 셀프 절차에서 표시되는 QR은 `DEMO-ONLY:SELF:` 토큰이며 감독관 인증 QR과 한 화면에 함께 표시되지 않습니다. 서버의 실제 QR 검사 및 입실 승인 API는 이 DEMO 코드를 명시적으로 거부합니다.

## 브라우저별 QR 스캔 체크리스트

최근 버전의 Chrome, Microsoft Edge, Firefox, Safari 및 Samsung Internet을 대상으로 네이티브 `BarcodeDetector` 또는 로컬 ZXing 대체 디코더를 사용하도록 설계했습니다. 브라우저 버전, 운영체제, 카메라 기기에 따라 실제 동작은 달라질 수 있으므로 아래 체크리스트로 배포 대상 기기에서 확인하세요. 이 개발 환경에는 실제 카메라가 연결되어 있지 않아 **카메라 스캔 성공은 검증되지 않았습니다**.

| 브라우저 | 카메라 점검 | 대체 경로 점검 | 결과 |
|---|---|---|---|
| Chrome 데스크톱/Android | HTTPS/localhost, 첫 권한 허용, 거부 후 설정 변경, 다른 앱 점유 상태 | PNG/JPEG 업로드, 잘못된 이미지, 수동 토큰 | 미검증 |
| Microsoft Edge 데스크톱/Android | HTTPS/localhost, 권한 허용/거부, 카메라 없음 | PNG/JPEG 업로드, 수동 토큰 | 미검증 |
| Firefox 데스크톱/Android | HTTPS/localhost, 권한 허용/거부, 카메라 없음 | PNG/JPEG 업로드, 수동 토큰 | 미검증 |
| Safari macOS/iOS | HTTPS/localhost, 사이트 권한, 전/후면 카메라 선택 | 사진 라이브러리 업로드, 수동 토큰 | 미검증 |
| Samsung Internet (Android) | HTTPS/localhost, 권한 허용/거부, 후면 카메라 | 갤러리 업로드, 수동 토큰 | 미검증 |

각 브라우저에서 확인할 항목:

1. `/api/health`가 응답하는 같은 서버의 HTTPS 또는 localhost 주소에서 페이지를 엽니다. 일반 LAN IP의 HTTP에서는 카메라를 사용할 수 없다는 안내가 표시되어야 합니다.
2. 감독관 로그인 후 카메라 허용/거부를 각각 확인합니다. 미지원 카메라 API, 권한 거부, 카메라 없음, 장치 점유 오류가 구분된 안내를 보여야 합니다.
3. 실제 발급 QR을 카메라로 인식한 뒤 서버 확인이 1회만 요청되는지, 응시자/감독관 수동 대조와 최종 승인이 계속 필요한지 확인합니다.
4. 같은 QR 이미지의 PNG/JPEG 업로드를 확인하고, QR이 없는 이미지·15MB 초과 파일·손상 파일도 확인합니다. 이미지 판독은 클라이언트에서 수행되며 판독된 토큰만 기존 서버 검증으로 전달됩니다.
5. 수동 토큰 입력, 만료 토큰, 이미 사용한 토큰, 다른 시험/응시자 토큰을 각각 검사해 서버에서 계속 차단되는지 확인합니다.
6. 중지 버튼, 탭 이동, 성공 판독 후 브라우저의 카메라 표시가 꺼지고 모든 MediaStream 트랙이 종료되는지 확인합니다.

외부 브라우저 테스트를 완료한 경우에만 체크리스트의 결과를 갱신하세요. 현 단계는 실제 브라우저/카메라 조합 검증을 완료한 것으로 간주하지 않습니다.

## QR 디코더 업데이트 및 라이선스

프로젝트는 `@zxing/browser` 0.2.1 (MIT)와 `@zxing/library` 0.23.0 (Apache-2.0)을 포함한 잠금된 의존성으로 `vendor/qr-decoder.min.js`를 빌드합니다. 배포용 번들과 포함된 의존성의 라이선스 전문은 `vendor/*-LICENSE.txt`에 있습니다. 개발자가 번들을 다시 만들 때는 Node.js 18 이상에서 실행합니다.

```sh
npm ci
npm run build:qr
```

애플리케이션을 실행할 때 Node.js는 필요하지 않습니다. 번들에 민감한 값이나 QR 토큰은 포함되어 있지 않습니다.

기본 SQLite 파일은 `exam_safe_pass.sqlite3`이며 저장소의 `.gitignore`에 포함되어 있습니다. 다른 위치를 쓰려면 `EXAM_SAFE_DB=/path/to/demo.sqlite3`를 지정합니다. 서버는 기본적으로 로컬 접속(`127.0.0.1`)에만 바인딩합니다. 포트 변경은 `EXAM_SAFE_PORT` 환경변수로 설정할 수 있습니다.

## 모의 인증 및 입실 흐름

1. 모의 인증은 `MockMobileIdProvider`만 사용하며 실제 모바일신분증 앱이나 정부 API를 호출하지 않습니다. 성공 증명은 `demo_mobile_id_auth`에만 저장되고 실패/성공 이벤트가 감사 기록에 남습니다.
2. 명시적인 DEMO 성공 결과가 있는 경우에만 서버가 `secrets.token_urlsafe(32)` 기반 `DEMO-ONLY:MOBILE:` QR을 발급합니다. 인증 증명은 1회만 사용하고 DEMO 토큰 원문은 응답에만 포함하며 DB에는 해시를 저장합니다. QR은 30초 후 만료됩니다.
3. DEMO QR 확인과 모의 입실은 DEMO 전용 API에서만 수행합니다. 감독관 권한, 토큰 만료·재사용·시험/응시자 불일치·중복 입실은 서버가 검사하며 모의 입실은 `demo_admissions`에만 기록합니다.
4. 운영 경로는 별도입니다. 현재 공식 provider와 기관 정책이 설정되지 않아 `/api/mobile-id/official-authenticate`, `/api/token`, `/api/token/inspect`, `/api/approve`의 운영 성공 경로는 fail closed입니다. DEMO 인증 증명, 브라우저 값, 직접 API 요청으로 이를 우회할 수 없습니다.
5. 관리자 감사 화면에는 mock 인증과 DEMO QR 발급·차단, DEMO 모의 입실 및 운영 경로 거부 이벤트가 구분되어 기록됩니다. 키오스크 관리자 테스트의 테스트 시나리오도 역할 검증을 통과해야 합니다.

## 안심패스 플러스 대체 확인 시연

응시자 첫 화면에서 모바일신분증 모의 인증, 실물 신분증 모의 확인, 현장 책임자 예외 확인 중 하나를 선택합니다. 이 절차의 결과는 시제품 시연용이며 모든 모의 입실은 `demo_admissions`에만 저장됩니다. 운영 `admissions` 기록을 생성하거나 운영 자격을 부여하지 않습니다.

- **실물 신분증:** 감독관은 원본 신분증, 응시원서 등록 사진, 현장 얼굴을 각각 직접 비교하고 결과를 입력합니다. 서버의 시제품 내부 모의 allowlist는 주민등록증·운전면허증·여권이며, 이는 주관기관이 실제로 허용한 문서라는 뜻이 아닙니다. 서버는 이 목록과 세 확인 결과가 모두 일치하는 경우만 1회 승인합니다. 신분증 종류 이외의 식별정보나 사진은 요청에 필요하지 않고 DB에도 저장하지 않습니다.
- **휴대전화와 허용 신분증이 모두 없는 경우:** 감독관의 `신원확인 보류` 요청만 기록되며 자동 승인되지 않습니다.
- **책임자 예외 절차:** 감독관 권한으로는 예외 승인을 할 수 없습니다. 별도 `supervisor` 역할로 로그인한 책임자만 시제품에 고정된 `dual_staff_application_review` 모의 절차를 승인할 수 있습니다. 응시원서 원본 확인, 등록 사진 대조, 직원 2인 입회, 책임자 확인을 모두 제출해야 합니다. 이 UI/서버 확인은 실제 절차 이행의 증거가 아니고 기관의 사전 승인도 아니므로, 실제 운영에서 입실 허가 근거가 될 수 없습니다.
- 모의 판정·거부·보류는 이벤트 기록에 `proctor` 또는 `supervisor` 행위자와 함께 남습니다. 확인 사진이나 신분증 개인정보는 감사 기록에 포함되지 않습니다. 모의 중복 입실은 `demo_admissions` 기본키와 트랜잭션으로 차단되며 운영 입실 기록은 변경하지 않습니다.

세 새 API는 `/api/physical-id/decision`(감독관), `/api/exception/decision`(현장 책임자 전용), 기존 `/api/dashboard`(관리자 감사 기록)입니다. 모의 시험 정책은 `MOCK_ALLOWED_ID_TYPES`와 `MOCK_EXCEPTION_PROCEDURES`에 고정되어 있으며, 외부 기관 정책이나 실제 자격증명을 자동 조회하지 않습니다. 이름·생년월일·수험번호 또는 사진 하나만으로 승인하는 경로는 제공하지 않습니다.

## 공식 모바일신분증 연동 준비 요건

현재 구현은 provider 경계와 mock 시연만 제공합니다. 공식 연동을 개발하거나 실제 인증으로 표시하기 전에 다음 자료와 승인을 담당 기관/공식 사업자에게 확인해야 합니다.

- **사전 승인 및 계약:** 연동 주체 자격, 사용 목적·범위에 대한 서면 승인, 이용 약관/계약, 운영 책임과 사고 대응 절차
- **공식 기술문서:** 지원되는 앱·SDK/API 방식과 버전, 인증·동의 흐름, 요청/응답 스키마, 오류 코드, 토큰 검증·서명 규칙, 키/인증서 발급·회전 및 폐기 절차
- **공식 테스트 환경:** 샌드박스 주소와 테스트 앱/계정/가상 자격증명, 테스트 데이터 정책, 승인된 네트워크·콜백 설정, 검수 및 운영 전환 절차
- **개인정보 보호:** 목적·법적 근거·고지/동의, 최소 수집 항목과 보유기간, 삭제·열람 요청 처리, 전송/저장 암호화, 접근권한·감사로그, 위탁·국외이전 여부, 침해 대응 및 개인정보 영향 검토
- **보안·운영:** 비밀정보 관리, TLS와 인증서 검증, 재전송 방지, 키 관리, 취약점 점검, 장애·타임아웃 처리, 감사 및 변경 승인

공식 문서와 승인을 받기 전에는 실제 서비스 주소·자격증명·개인정보를 추가하지 말고 `MockMobileIdProvider`만 사용하세요. 공식 provider를 추가할 때도 동일 인터페이스에 별도 구현으로 연결하고, 승인된 샌드박스·테스트 절차를 통과하기 전 운영 인증으로 표시하지 않아야 합니다.

토큰은 QR용 임의 식별자이며 이름, 수험번호 등 개인정보를 담지 않습니다.

## 테스트

저장소 루트에서 아래 명령이 기본 활성 Python 테스트 전체를 실행합니다. JavaScript 얼굴 비교 테스트도 이어서 실행합니다.

```sh
python3 -m unittest discover -v
node --test tests/test_face_similarity.js
```

`unittest discover`는 루트의 `test_scenarios.py` HTTP 통합 테스트와 `tests/`의 provider·fail-closed 및 활성 UI 회귀 테스트를 함께 실행합니다. 수정 전 스냅샷 테스트 21개 파일은 `test_backups/`에 원본 그대로 보관하고 기본 검색에서 제외했습니다. 이 디렉터리는 Python package가 아니므로 표준 unittest 탐색은 하위 테스트를 재귀 검색하지 않습니다. 보안 경계 테스트는 DEMO 인증 증명의 운영 QR 발급 거부, DEMO QR의 운영 검사·승인 거부, DEMO 모의 입실이 `admissions`를 생성하지 않고 `demo_admissions`만 기록하는지, 공식 provider 미연결 시 운영 API fail closed인지 검증합니다. 기존 통합 테스트에서는 QR 발급·만료·재사용 차단, 중복 입실, 키오스크 흐름 및 인쇄용 QR TTL/상태도 확인합니다.

이 자동 테스트들은 실제 브라우저 화면·카메라 동작 또는 프린터 출력을 검증하지 않습니다. 실제 기기별 검증은 위 체크리스트에 따라 별도로 수행해야 합니다.
